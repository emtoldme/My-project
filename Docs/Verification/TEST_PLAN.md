# 分阶段验证计划

2026-10-12 用户决定：初期测试不必严格，完备测试在中后期有计划进行；必要且适合人判断的检查由用户完成，其余自动化由 Codex 完成。

## S1：原型轻量验证

每次 PR 检查修改范围与依赖；代码变化运行已有快速规则测试。整合 Unity 脚本或资源后确认编译、场景启动及引用完整；只检查本轮受影响的关键路径。产生可试玩版本时做一次短流程检查与构建，不要求每个小 PR 全量打包、压力测试、录像或设备矩阵。

关键路径逐步覆盖：移动/攻击/闪避 → 伤害与死亡 → XP/升级 → 暂停/恢复 → 终局/重开。已发现的崩溃、编译失败、核心流程卡死、资源丢失或重复关键结算当轮修复；轻微表现问题记入任务板。

用户只评估已经准备好的试玩包和对比材料：手感、镜头可读性、视觉方向、听感以及阶段是否通过。Codex 负责依赖还原、Git LFS、Unity 导入、.meta、场景生成、日志整理与自动验证，不把这些交给用户执行。

## S2–S3：视听与构筑稳定后补回归

在对应系统接口稳定时补充高价值边界测试：真实输入切换、暂停/升级期间行为、连续升级、对象回收、重复命中/死亡奖励、无效目标、持续音效/特效清理与重开。每个阶段候选包跑完整关键流程，并实测音频循环、画面可读性与基础性能。

此时建立固定压力场景和记录方式，先测30/100敌人，再按真实设备决定是否扩至200。统计CPU/GPU帧时间、GC、内存与活跃实体，不把目标当作实测成绩。

## S4–S5：完整一局与性能稳定

构筑、升级和12分钟流程成形后，执行多局长时间运行、不同配置/分辨率/输入设备、窗口切换、暂停与重开组合检查；验证资源加载、声音并发、池容量和逐局内存变化。形成可重复的回归用例和固定版本性能基线。

## S6：发布候选

在目标设备上验证发行构建、首次运行、设置持久化、完整流程、资源来源与署名、包内容和已知问题。将自动结果、人工体验和未覆盖范围分别记录，由用户最终验收。

验证结论始终绑定具体提交与范围；没有实际执行的项目标记待验证。调整测试强度不等于提前宣布系统或阶段通过。
